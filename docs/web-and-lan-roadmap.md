# Web 前端与局域网联机实施计划

本文是后续开发的默认路线图。R1–R3、阶段 0–4 及阶段 5 的主要交互切片已完成自动化验收，家庭局域网实机验证通过；
整体顺序为：

```text
现有 Python 规则引擎
        ↓
✅ R1：类型化规则、效果、观察与状态组件
        ↓
✅ R2：显式阶段解析器与可扩展流程
        ↓
✅ R3：完整迁移 FS / BTX，并用其他规则集压力测试
        ↓
✅ 阶段 0：稳定 JSON 接口
        ↓
✅ 阶段 1：本地单机 Web 前端
        ↓
✅ 阶段 2：本地完整对局调试与修正
        ↓
✅ 阶段 3：房间、座位和局域网同步
        ↓
✅ 阶段 4：2–4 人可变人数与动态控制权
        ↓
交互与视觉增强
```

除非实际试玩发现基础架构无法满足需求，不跨阶段同时开发大型功能。R1–R3 未通过验收前，
不开始 React、房间或局域网功能。规则结算始终只由 Python
后端负责；Web 前端不得复制身份、事件、胜负或能力规则。

## 目标与边界

最终目标是让一台电脑作为家庭局域网主机，2–4 名玩家使用各自的电脑或手机加入完整对局。
同一 Wi-Fi 下，只要路由器未启用客户端隔离、主机防火墙允许服务端口，玩家应能直接通过
`http://<主机局域网地址>:<端口>` 访问。

首轮开发不包含：

- 公网大厅、账号、好友、匹配和长期云存档；
- 防止参与者主动作弊；
- 内置语音或文字聊天；
- 复杂动画、完整移动端手势和素材编辑器；
- AI 玩家；
- 重写 Python 规则引擎或删除现有 Tk/CLI 前端。

网络层仍须防止普通误操作与低成本攻击，包括不可猜测令牌、输入校验、请求大小限制、基本限流、
路径隔离和服务端行动验证。

## ✅ 前置阶段 R1：规则与模拟基础抽象（已完成）

目标是把当前集中在 `Game` 中的规则逻辑变成可组合、可检查的领域对象，同时保持现有
`dispatch`、`legal_actions`、`simulate`、`view`、存档、replay 和 JSON 接口兼容。

不采用多重继承 mixin 或全局广播 hook。底层采用显式调用关系：

```text
阶段解析器决定何时查询规则
        ↓
规则集返回 Activation / ActionOffer
        ↓
结算器执行 Effect
        ↓
观察层生成玩家可见 Observation
        ↓
完整 ResolutionTrace 留给调试和完整回放
```

### R1a：规则集能力矩阵

在冻结接口前，盘点全部现有规则集的扩展维度：

- 额外资源和跨轮回状态；
- 单身份、双身份、身份宣称和玩家秘密；
- 基础出牌以外的玩家行动；
- 阶段插入、阶段替换和特殊终局；
- 角色、版图、尸体或附着物上的额外状态；
- 立即失败、轮回结束判定和非标准获胜者；
- 对外现象与真实原因之间的信息边界。

至少覆盖以下架构压力点：

| 规则集 | 压力点 |
| --- | --- |
| MZ | Ex、身份宣称、伪造事件的公开名与真实事件 |
| MC | Ex 槽、行动限制和特殊剧作家放置 |
| HSA | 尸体标记、版图诅咒和群聚事件 |
| WM | 跨轮回 Ex、主人公法术、规则替换 |
| AHR | 表里世界、双重身份、希望/绝望牌 |
| LL | 玩家秘密、背叛者、特殊胜利和最后的战斗 |

产物是一张代码内外一致的能力矩阵和一组架构适配测试，而不是立即搬迁全部规则实现。
当前盘点结果见 [规则集能力矩阵](ruleset-capability-matrix.md)。

### R1b：领域对象

引入以下类型，并允许现有字典效果通过临时适配器逐步迁移：

- `RuleContext`：规则只读访问当前剧本、状态和时间点；
- `ActionOffer`：任意玩家可执行行动，包含稳定 kind、actor、timing、source 和结构化参数；
- `Activation`：已经满足条件的强制或可选能力；
- `Effect` / `EffectResult`：类型化状态变化、后续选择和中断结果；
- `Observation`：特定玩家实际可见的结构化现象；
- `ResolutionTrace`：包含真实来源的完整因果记录；
- `StateComponent`：规则集专属且可复制、序列化的类型化状态；
- `PhaseKey` / `FlowPlan`：允许规则集注册名字空间阶段或替换终局；
- `VictoryPolicy` / `EndgamePlan`：规则集化的失败、轮回结果和终局流程。

基础行动可以使用 `core.play_card`，WM 法术可以使用 `wm.cast_spell`，LL 终局操作可以使用
`ll.final_battle.*`。MCTS 和网络客户端只枚举 `ActionOffer` 并调用状态转移，不解析行动显示文本。

`GameState` 分成基础状态和已注册组件。规则定义、角色定义和本地化目录为不可变共享数据，
不得随每次 `simulate` 深复制。第一版继续采用可靠的显式状态复制；在基准测试后才考虑结构共享或可逆增量。

### R1c：异常机制架构适配测试

在完整迁移 FS/BTX 前，为以下机制各建立一个最小适配原型：

- WM 法术能作为主人公能力时间点的额外 `ActionOffer`；
- AHR 世界切换能作为专用 Effect 和状态组件；
- LL 最后的战斗能替换标准终局计划；
- MZ 身份宣称能同时保存真实身份和公开说法；
- HSA 版图诅咒能存在于角色之外的状态组件。

这些测试只验证抽象承载能力，不在 R1 提前迁移整个规则集。任何原型都不得用规则集名称条件分支
绕过新接口。

R1 验收条件：上述机制都能由同一套 Action、Activation、Effect、Observation 和状态组件契约表示；
现有完整测试、存档和 replay 仍然通过。

实施状态：R1 已完成。旧字典效果通过 `normalize_effect` 兼容，新代码可直接使用类型化契约；五类复杂规则
均有架构压力测试，且尚未改变 JSON 协议。

## ✅ 前置阶段 R2：阶段与结算器拆分（已完成）

将流程从 `Game` 拆到独立阶段解析器：

```text
tragedy_sim/phases/
├── day_start.py
├── action_cards.py
├── action_resolution.py
├── mastermind_abilities.py
├── protagonist_abilities.py
├── incidents.py
├── day_end.py
├── loop_end.py
└── final_guess.py
```

每个解析器负责本阶段的合法行动和状态推进；规则内容来自当前 `RulesetDefinition`。
核心时间点保持稳定，但玩家输入阶段采用可注册的名字空间 `PhaseKey`，例如
`core.protagonist_abilities` 和 `ll.final_battle`。

同一时间点使用固定结算协议：

1. 在同一状态快照上收集全部强制 Activation；
2. 固定已经触发的能力；
3. 完成必要的顺序和目标选择；
4. 结算全部强制效果；
5. 查询当前仍可发动的可选能力；
6. 由对应玩家决定发动与结算顺序；
7. 离开时间点。

`Game` 最终只保留稳定外部门面、当前状态和协调入口，不直接包含具体角色、事件或规则集条件。

R2 验收条件：完整对局通过阶段注册表运行；现有强制/可选顺序、信息过滤和原子回滚测试不变；
每次结算能输出明确 Activation、Effect、Observation 和内部 Trace。

实施状态：R2 已完成。完整对局通过不可变阶段注册表分派，注册表允许规则集显式增加带名字空间的阶段或
替换单个核心阶段；扩展阶段自行声明时间点、控制者、命令结构和状态推进。强制能力时间窗先在脱离运行态的
快照上固定触发集合，生命周期阻止在强制效果完成前查询可选能力。运行时保留私密 Activation 历史，效果与
跨人类选择的后续效果均携带稳定来源，直接 Observation 进入对应 ResolutionTrace，不会因递归结算重复归因，
也不会进入任何玩家视图。旧字典效果仍由显式兼容处理器组合运行；规则集可以逐项改为类型化 Effect。

## ✅ 前置阶段 R3：迁移 FS 与 BTX（已完成）

建立规则集目录和注册表，首先完整迁移 FS、BTX：

```text
tragedy_sim/rulesets/
├── base.py
├── registry.py
├── common/
├── fs/
│   ├── definition.py
│   ├── plots.py
│   └── incidents.py
└── btx/
    ├── definition.py
    ├── roles.py
    ├── plots.py
    └── incidents.py
```

规则集和剧本保持分离：`RulesetDefinition` 描述公开规则全集，`ScriptDefinition` 描述本局秘密配置，
`GameState` 描述当前事实，`InformationState` 描述某位玩家根据 Observation 获得的知识。

R3 工作项：

1. 抽出 FS/BTX 剧本校验、身份、规则 X/Y、事件和胜负策略。
2. 删除 `Game` 中对应的规则集名称分支。
3. 为规则集建立共同契约测试和 FS/BTX 专项测试。
4. 验证 CLI、Tk GUI、JSON、存档和 replay 的外部兼容性。
5. 建立 `transition(state, action)` 和显式 clone 的基准，记录迁移前后模拟吞吐。
6. 确保 WM/AHR/LL/MZ/HSA 的 R1c 架构适配测试仍通过。

R3 验收条件：FS 和 BTX 不再依赖巨型 `Game` 中的专属规则逻辑；完整测试通过；公开 Observation
不泄露隐藏来源；相同状态和命令得到确定性相同结果；其他规则集未来迁移不要求修改底层核心契约。

实施状态：R3 已完成。FS 与 BTX 分别从 `rulesets/fs`、`rulesets/btx` 组合自己的校验器、事件入口、
终局能力和基础效果集合，不导入兼容规则模块。`ScriptDefinition`、运行态与 `InformationState` 已分离，
规则集和剧本定义在搜索克隆间共享；`clone`、`transition` 和类型化 `ActionOffer` 构成统一模拟入口。
CLI、Tk GUI、JSON 服务、存档和文本 replay 均继续使用同一 `dispatch` 语义，并由全套测试覆盖。
基准可用 `python -m benchmarks.clone_simulation --iterations 1000` 重跑；开发机 300 次样本约为
11,503 clone/s、4,952 transition/s，且确认规则集与剧本定义不被深复制。

R1–R3 预计合计 8–12 个工作日。每个阶段独立提交；行为修复与纯结构搬迁分开提交。

## 重构后的规则集迁移

Web 开发只要求 R1–R3 完成，不要求先迁移所有复杂规则集。但未迁移规则集必须继续通过兼容适配器完整运行。
其余规则集后续按下列顺序逐个迁移，并各自单独提交：

```text
MZ → MC → HSA → WM → AHR → LL
```

如果某个规则集要求修改核心 Action、Activation、Effect、Observation、StateComponent 或 FlowPlan 契约，
应先停止迁移，补充压力案例并审查抽象；不得直接增加新的 `if module == ...` 到核心阶段或结算器。

## AI 与身份反推约束

重构阶段不实现真正的 MCTS，但新边界必须支持后续 Information Set MCTS：

- `legal_actions` 返回结构化行动，搜索器不理解具体规则集文本；
- `transition` 对给定状态和行动保持确定性；
- 隐藏剧本采样和对手策略随机性由 AI 层显式注入；
- 每位玩家只根据自己的 Observation 构造 `InformationState`；
- 完整 Trace 不能进入主人公 Observation；
- 强制能力未出现与可选能力未出现具有不同的推理意义；
- 身份候选通过结构化现象、时点和公开状态筛选，不解析日志句子。

性能优化以基准为依据。初期优先保证状态复制正确，不提前采用容易污染搜索树的 make/unmake 可逆状态方案。

## ✅ 阶段 1：本地单机 Web 前端（已完成）

推荐采用 React、TypeScript 和 Vite。第一版只连接本机 Python 服务，并用一个开发用座位切换器访问
各视角；它是调试工具，不是最终热座产品。

### 1.1 工程骨架

- 新建独立 `web/` 目录。
- 配置 TypeScript、ESLint、Vitest 和开发代理。
- 建立 API client、错误类型、revision 管理和统一请求取消。
- Python 开发服务器允许 Vite 的本地 Origin；生产构建由 Python 服务静态托管。
- 保留 CLI、Tk GUI 和服务端原有启动方式。

实施状态：以上工程骨架均已完成；生产构建由 Python 服务安全地静态托管。

### 1.2 最小可玩界面

页面至少包含：

- 规则集/剧本选择和新建对局；
- 当前轮回、日期、阶段、规则时间点和当前操作者；
- 四区域棋盘、角色、存活状态与所有公开标记；
- 当前视角的手牌、已公开留置牌和暗牌目标；
- 合法行动、合法目标、必要选择和确认按钮；
- 事件日程、公开知识、规则速查和完整公开日志；
- 剧作家秘密资料，仅在剧作家调试视角出现；
- 保存、恢复、导出 replay 和只读 replay 浏览。

第一版出牌使用“选择手牌 → 选择目标 → 确认”。拖拽不是进入本地试玩的前置条件。

实施状态：最小界面已覆盖规则集/JSON 剧本、四区域棋盘、特殊资源、私密手牌、暗牌、合法行动、
公开知识、规则速查、事件状态、日志、胜负、snapshot 及 `.tlr` 查看/导出。座位切换器明确保留为本地调试工具。

### 1.3 状态管理约定

- 服务端视图是唯一权威状态，不在前端预测规则结算。
- 前端只保存短暂 UI 状态，例如已选手牌、展开面板和日志滚动位置。
- 每次提交使用服务端提供的 `action_id` 和当前 revision。
- 收到 `STALE_REVISION` 后刷新视图和合法行动，并取消过期选择。
- 切换视角时清除所有私密 UI 状态和缓存响应。

实施状态：客户端只按稳定行动 ID 和 revision 提交；过期 revision 会刷新服务端视图，行动组件随合法行动集合
重建，切换视角会先清空视图、行动选择和回放面板。

验收条件：用浏览器从新建剧本运行到正式胜负，包含能力、拒绝、事件、必要目标、轮回重置、最终猜测和 replay。

## ✅ 阶段 2：本地完整调试（已完成自动化验收）

5. 人工试玩：FS 已完成基础试玩；其余规则集试玩不阻塞阶段 4，集中放到交互优化后再次验收。

- 主人公永远看不到身份、实际规则、事件当事人和剧作家私密选项；
- 时间点正确区分日终失败、轮回结束效果和最终猜测；
- 后端状态变化后旧按钮不能再次提交；
- 手机窄屏仍能完成所有行动，即便尚未美化；
- 刷新页面不会破坏当前本地调试对局。

退出条件：不存在阻断完整对局的前端问题，公开/私密信息边界通过自动测试和人工审查。

## ✅ 阶段 3：房间与局域网联机（已完成单机自动化验收）

完成本地调试后，加入独立于 `GameService` 的房间层。房间负责座位和连接生命周期，
`GameService` 继续负责游戏状态、权限与规则。

### 3.1 房间模型

房间至少保存：

- 随机房间码、创建时间和最后活动时间；
- 房主管理令牌；
- 对应的游戏 session；
- `m/a/b/c` 座位、昵称、准备状态和断线状态；
- `waiting`、`playing`、`finished` 状态；
- 可选的旁观者开关。

建议接口：

```text
POST /v1/rooms
GET  /v1/rooms/{room_code}
POST /v1/rooms/{room_code}/join
POST /v1/rooms/{room_code}/ready
POST /v1/rooms/{room_code}/start
POST /v1/rooms/{room_code}/leave
GET  /v1/rooms/{room_code}/updates
```

玩家领取座位后获得独立、不可猜测的座位令牌。浏览器本地保存令牌以支持刷新与短暂断线重连；
房间码本身不能读取剧作家或主人公私密数据。房主可以释放误占座位、关闭房间和导出存档。

### 3.2 同步策略

第一版采用 1 秒左右的条件轮询：客户端携带已知 revision，仅在状态变化时重新取得视图和行动。
它足以支持回合制游戏，部署和排错成本最低。运行稳定后可改为 SSE；暂不使用 WebSocket。

任何客户端都不能上传完整游戏状态。所有行动仍通过稳定 `action_id` 提交并由服务端验证座位和 revision。

### 3.3 局域网启动体验

新增面向房主的启动方式，例如：

```powershell
python -m tragedy_sim --host-room --port 8765
```

启动后应显示：

- 本机地址 `http://127.0.0.1:8765`；
- 检测到的局域网地址，例如 `http://192.168.1.23:8765`；
- 房间创建入口；
- Windows 防火墙和访客 Wi-Fi/客户端隔离提示。

只显示经过验证的私有局域网地址，不自动配置路由器、不自动做端口转发，也不声称该链接可从互联网访问。

### 3.4 最低安全要求

- 房间码、管理令牌和座位令牌使用密码学安全随机数。
- 一个座位默认只能被一个有效令牌占用。
- 所有请求限制正文大小、字段集合、字符串长度和频率。
- 静态文件只能来自构建目录，不能把任意文件路径暴露为 URL。
- 错误响应不包含秘密、堆栈、文件系统路径或其他座位令牌。
- 房间长时间无活动时自动清理；正在进行的房间使用更长超时。
- 默认仍监听 `127.0.0.1`；只有显式房主命令才监听局域网接口。

验收条件：四台设备连接同一家庭 Wi-Fi，各自领取不同座位，完成一局游戏；刷新和短暂断线可以恢复，重复提交和越权请求被拒绝。

实施状态：房间服务已独立封装座位、昵称、准备、在线状态、房主管理、过期清理及游戏凭据映射；React 大厅支持
邀请链接、占座、准备、释放座位和固定私密视角。客户端以一秒条件轮询同步两个 revision，刷新可恢复席位。
四个隔离浏览器上下文已自动验证建房至开局、信息边界、行动同步和刷新重连；家庭局域网多浏览器实机联机已由用户
验证通过。其余不同设备组合和长局断线恢复继续作为后续回归项目。

## ✅ 阶段 4：2–4 人可变人数与动态控制权

### 4.1 目标与人数规则

支持总共 2–4 名真人参与，同时不改变规则引擎中固定存在的 `m/a/b/c` 四个逻辑席位：

| 真人构成 | 逻辑席位控制方式 |
| --- | --- |
| 1 名剧作家 + 3 名主人公 | 三名主人公分别固定控制 A、B、C；沿用当前规则中的 A → B → C 领队轮换 |
| 1 名剧作家 + 2 名主人公 | 两人各固定控制 A、B；第三个逻辑席位 C 的“行动牌”由当天真人领队代管；两名真人领队逐次交替 |
| 1 名剧作家 + 1 名主人公 | 该主人公同时控制 A、B、C 的所有主人公操作 |

最低必须有一名剧作家和一名主人公。房间创建时选择主人公真人数量，开始条件由“四个逻辑席位坐满”改为
“一名剧作家和所选数量的主人公参与者均已入座并准备”。对局开始后不得改变人数或控制分配。

两人主人公模式中，“当天真人领队”在每次规则引擎发生领队轮换时在两名真人之间交替；轮回提前结束不会凭空
多轮换一次。必须在界面明确显示真人领队、引擎当前逻辑领队，以及该日谁代管 C，避免把两种概念混为一谈。

### 4.2 参与者与逻辑席位分离

房间层新增稳定的 `Participant`，令牌属于真人参与者，不再直接等同于单个逻辑席位。规则引擎、存档、replay、
AI 的 `ActionOffer` 和 `transition` 仍只认识 `m/a/b/c`，不加入“当前有几名真人”的规则分支。

房间层根据当前状态生成显式 `ControlAssignment` / `ControlGrant`：

- 固定控制权：剧作家 → `m`，主人公参与者 → 自己的 A/B/C；
- 临时出牌权：两主人公模式的当天真人领队 → C 的 `core.play_card`；
- 团队决策权：当前真人领队 → 引擎要求由逻辑领队执行的友好能力、事件选择、提前最终猜测等行动；
- 单主人公模式：该参与者 → A/B/C 的所有主人公行动；
- 每项授权都包含 actor、行动种类和有效 revision/时间段，不能仅用一个宽泛的“可控制多个座位”布尔值。

服务端先枚举原引擎的合法行动，再按控制授权过滤；提交时重新计算授权并校验 revision。客户端不能自行声明正在
代管哪个座位，也不能因为曾在前一天代管 C 而继续提交 C 的行动。行动日志和 replay 继续记录真实逻辑 actor，
另外记录执行该操作的真人参与者昵称，便于回看但不影响确定性重演。

### 4.3 私密信息边界

多席位控制不能简单地把多个 `game.view(seat)` 字典合并。网络响应应返回公共棋盘、参与者当前获准查看的分区手牌，
以及按规则授权的个人秘密；切换领队或临时控制权时清除已经失效的前端缓存和选择。

- 单主人公模式中，同一真人必然能看到 A/B/C 的全部主人公私密信息；界面应明确提示这是该人数变体的固有差异。
- 两主人公模式中，代管 C 默认只授予当天 C 行动牌的查看与提交权限，不自动授予 C 的其他个人秘密。
- LL 包含每位主人公独立秘密、背叛者和特殊胜利，因此强制使用三名主人公真人（总计四人），不开放缩减人数模式。

### 4.4 前端与协议调整

大厅改为“剧作家席位 + 1–3 个真人主人公席位”，而不是直接展示四个引擎席位。进入对局后：

- 顶部同时显示当前真人领队和逻辑领队；
- 手牌按 A/B/C 分组，每组标明固定控制或“今日由你代管”；
- 同一真人可行动的多个逻辑 actor 由后端返回，前端仍只提交稳定 `action_id`；
- 非当前控制者能看到公开的等待提示，但不能请求对应暗牌或行动列表；
- 刷新、短暂断线和多标签页仍恢复同一个参与者及当前动态授权。

房间协议已向后兼容扩展为 `protagonist_count`、`required_seats`、`human_leader`、`logical_leader` 和按请求
计算的动态行动授权，保留
`m/a/b/c` 作为游戏视图和行动中的逻辑 actor。现有四人房间数据视为 `protagonist_count = 3`。

### 4.5 测试与验收

1. Python：分别用 1、2、3 名主人公参与者完成一局，所有行动仍由同一个确定性引擎结算。
2. 权限：验证两人模式中 C 仅能由当天真人领队出牌，轮换后旧令牌和旧 action ID 均失效。
3. 顺序：同一参与者控制多个逻辑席位时，仍服从引擎给出的出牌顺序，不允许提前代打。
4. 信息：逐规则集检查多视图组合，重点覆盖 LL 个人秘密、背叛者和 AHR 最终猜测。
5. 浏览器：2、3、4 个隔离上下文分别完成建房、准备、至少一次领队轮换、刷新重连和正式胜负。
6. replay：显示真人执行者与逻辑 actor，同时能用原始逻辑命令确定性重演到相同终局。

验收条件：总人数 2、3、4 人都能在局域网完成对局；任何参与者只能看到并执行当前授权内容；四人模式行为和现有
存档/replay 完全兼容；规则引擎和规则集不需要知道真人数量。

实施状态：Python 已验证一名和两名主人公玩家均可完成完整对局，既有四席位完整对局测试保持通过；权限测试覆盖
C 代管、真人领队轮换、私密手牌、非法人数和错误命令。Playwright 已用 2、3、4 个隔离浏览器上下文验证建房、
入座、准备、开局和动态出牌。LL 在接口与界面均强制四人。房间 replay 会以注释记录真人执行者，同时继续用原始
逻辑命令通过确定性校验。家庭 Wi-Fi 已由多个浏览器和手机实机确认可用；其余规则集人工试玩仍按计划后置，
不阻塞本阶段自动化完成。

## 阶段 5：交互、素材和视觉增强

联机主流程稳定后，再逐项加入：

1. 使用 `dnd-kit` 的拖拽出牌，同时保留点击操作作为移动端和无障碍后备。
2. 拖动时只高亮服务端 `actions` 中存在的合法目标。
3. 根据人工维护的素材 manifest 展示角色、行动牌、事件和规则图片。
4. 从原图生成适合网页的 WebP 缩略图；不改变或覆盖 `resources/` 原件。
5. 增强日志过滤、时间点分组、角色浮层、标记动画和 replay 时间轴。
6. 在公开发布图片素材前单独确认授权和分发范围。

这些增强不得改变网络协议中的规则含义，也不得成为完成行动的唯一方式。

### ✅ 5.1 主界面与移动端信息层级

第一切片把当前时间点与“现在是否轮到你”提升为独立状态条，将行动区移到棋盘之前；桌面端规则资料栏固定在可视区域，
移动端使用双列紧凑状态、两列手牌和底部确认条。所有合法性仍完全来自服务端 `actions`，原有点击操作、键盘焦点、
窄屏无横向滚动和自动化选择器保持兼容。

### ✅ 5.2 拖拽与合法目标高亮

行动牌支持鼠标、触屏和键盘传感器拖拽；拿起一张牌时只显示该牌在服务端 `actions` 中存在的目标，悬停目标会
高亮。放下后仍需明确确认，且原有“点击牌 → 点击目标 → 确认”流程完整保留。短暂延迟确认条以避开触屏拖放结束
时浏览器的点击抑制窗口，防止第一次确认被吞掉。Playwright 覆盖了从拖起、合法落点到真实命令提交的完整流程。

### ✅ 5.3 素材 manifest 与缩略图

构建脚本从 `resources/data.xml` 校验角色、四席位基础手牌和 AHR 追加牌的稳定映射，不依赖界面显示文字猜测牌义；
使用 `sharp` 生成独立的 180px WebP 文件，不改变原始 PNG。当前 59 张去重素材合计约 548 KB，适合家庭 Wi-Fi
首次加载，并使用浏览器缓存与惰性加载。界面在角色、手牌和拖拽浮层显示图片；素材缺失或加载失败时只隐藏图片，
文字操作始终可用。素材来源仍是仓库中用户提供的社区资源，扩大公开分发范围前需另行确认授权。

### ✅ 5.4 日志筛选及 replay 时间轴

公开日志按后端提供的轮回、日期和 `timepoint` 分组，可切换“今日 / 本轮回 / 全部”并搜索时间点或消息；筛选仅影响
展示，不改变或丢弃日志。完整信息 `.tlr` 回放会转换为可逐项选择的决策时间轴，分别显示玩家决策和该决策产生的
结算步骤，支持前后步、滑杆定位与移动端横向时间轴，并始终保留原始纯文本供核对、下载和兼容旧工具。

### ✅ 5.5 版图直接交互

版图调整到行动牌上方。选牌或开始拖动后，服务端给出的合法角色和版图直接高亮，可点击或作为拖放目标；不再生成
重复的目标按钮。行动牌只显示牌名与图片，不显示目标数量或“可拖拽”说明。行动选项新增不含规则含义的 `ui.source`
提示，使友好能力和身份能力可以先从版图选择发动角色，再选择该角色当前可用的能力；前端不解析中文能力名称。
选定目标后的确认条固定在视口底部，避免从版图来回滚动。

仍未实现：角色资料放大浮层、计数物变化动画、其余规则集的集中人工试玩，以及图片素材扩大公开分发前的授权确认。
