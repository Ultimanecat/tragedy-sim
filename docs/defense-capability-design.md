## 先修正一个错误

之前的防守模型只把“计数器变化”当成两类东西：

- 行动牌：`p-1`、`g1/g2`、`fi`、移动牌。
- 事故本身：阈值到了就失败。

这套模型漏掉了**角色友好能力**。角色能力可以改计数器、转移计数器、移动角色、阻止事故，而且往往需要提前几天做铺垫。大小姐自杀因此被误判成“结构性失败”。

BTX01 里就有一个被漏掉的防守手段：

- 鉴识官 `forensic` 的 `transfer` 能力：在**同区域另两名角色**之间移动一个计数物。
- 触发需要鉴识官友好达到阈值 2。
- 它可以把大小姐的不安移到另一个角色身上，直接降低自杀风险。

所以防守设计要从“卡牌计数器”升级成“能力链”。

## 目标

把防守从：

```text
义务 -> 当天有没有 p-1
```

改成：

```text
义务 -> 可用能力链 -> 需要的前置条件 -> 跨日铺垫计划 -> 当天行动
```

## 核心抽象

### 防守能力

```text
DefenseCapability
- source          角色 id 或卡牌 family
- kind            counter / adjust / transfer / move / block / prevent
- counter         paranoia / goodwill / intrigue / guard
- amount          变化量
- scope           self / same / other / same_or_location / any
- threshold       友好或能力阈值
- once_per        day / loop / game
- preconditions   活着、在场、同区域、目标数、可行动
- collateral     可能带来的副作用
```

### 能力链

一条能力链是若干步骤：

1. 铺垫：加友好、移动角色、清理阻挡。
2. 触发：使用能力，改变计数器或位置。
3. 收尾：处理被转移到的目标，或补一张牌。

每条链有时间要求：最早哪天可开始、最晚哪天必须完成、需要哪些牌和角色位置。

### 防守计划

```text
DefensePlan
- obligation       要防的事故
- chains           可行能力链
- chosen_chain     当前选择
- setup_days       需要提前铺垫的天数
- reserved         需要保留的牌或能力
- collateral       副作用评估
```

## 能力来源

第一版先覆盖规则里最常见的几类：

| 类型 | 例子 | 作用 |
| --- | --- | --- |
| `counter` | 加友好、加/减不安 | 直接改计数 |
| `adjust` | 医生：同区域另一角色不安 ±1 | 定向改计数 |
| `transfer` | 鉴识官：同区域两名角色间移动计数 | 把危险计数移走 |
| `reset` | 学者：移除自身计数 | 自保 |
| `move` | 移动角色 | 调整同区域关系 |
| `guard` / `prevent_incident` | 护卫、阻止事故 | 直接取消失败 |
| `block` | 禁止密谋、禁止移动 | 阻止后续变化 |

卡牌也作为能力来源：

- `g1/g2`：给能力角色加友好，铺垫阈值。
- `p-1`：直接降不安。
- `fi`：阻止密谋变化。
- `h/v/d`：移动角色，满足同区域条件。

## 规划方式

### 1. 算缺口

对每条义务算：

```text
缺口 = 当前计数 + 预期黑方增量 - 安全上限
```

大小姐案例：上限 1，所以安全上限是 0。

### 2. 找能力链

对缺口枚举：

- 直接 `p-1`。
- 鉴识官 `transfer`：需要鉴识官友好 2、同区域至少两名其他角色。
- 医生 `adjust`：需要医生同区域、友好 2。
- 学者 `reset`：只处理自身。
- 阻止事故能力。

每条链记录：

- 最早可启动日；
- 每天能提供的减量；
- 需要几张牌、几次能力；
- 对接收目标的副作用。

### 3. 反推铺垫

如果选 `transfer`：

- 最晚在事故日前把鉴识官友好提到 2。
- 把鉴识官和大小姐放进同一区域。
- 同区域还要有第三个角色作为计数接收者。
- 接收者不能是马上会触发事故的角色。

如果接收者会因此接近阈值，需要第二条能力链处理它。

### 4. 资源约束

- 每个角色每天只能被放一张牌。
- 能力一般每天一次。
- 同一张限次牌只能用一次。
- 移动和加友好会占用当天牌位。

规划器要在“提前准备”和“当天救火”之间取舍。

### 5. 和执行层的关系

规划器输出 `DefenseIntent`：

```text
今天应该做：给鉴识官 g2 / 把鉴识官移到学校 / 用 transfer 把大小姐不安移到班长
理由：大小姐第 5 天自杀，缺口 2，transfer 是最省牌的链
```

行动层把 intent 转成候选和评分，仍然由搜索比较，不直接覆盖行动。硬覆盖已经验证会变差。

## BTX01 大小姐案例

事实：

- 大小姐上限 1，任何不安都会在事故日触发自杀。
- 剧作家可以用暗牌和传谣能力持续加不安。
- 单靠 `p-1` 每天减 1，抵消不了总增量。
- 但鉴识官可以把不安移走。

一条可能的防守链：

1. 提前给鉴识官加友好到 2。
2. 把鉴识官移动到大小姐所在区域。
3. 保证同区域还有第三个角色作为接收者。
4. 在事故前用 `transfer` 把大小姐的不安移给接收者。
5. 如果接收者累计不安，安排第二条链处理，或换一个安全接收者。

这条链需要：

- `g1/g2` 铺垫；
- 移动牌调整位置；
- 鉴识官存活；
- 每天一次转移；
- 对接收者的二次管理。

这不是“当天一张 `p-1`”能表达的，正是之前模型缺失的部分。

**注意**：以上是设计推演，尚未用引擎跑通。下一步必须写一个脚本化能力链测试，确认大小姐不安能在事故日前降到 0。

## 验证计划

1. 写能力目录提取：从角色定义和规则里读出 `transfer/adjust/reset/guard/prevent`。
2. 写一个脚本化 BTX01 防守计划，用真实引擎逐步执行，检查大小姐事故日的不安是否低于 1。
3. 跑通后，把同一计划接入行动层，与当前粒子红方做同种子对比。
4. 再看其他剧本的跨日失败条件，确认能力链能不能复用。

## 风险

- 能力链的前置条件多，规划空间会变大。
- 转移会把风险转给另一个角色，可能制造新事故。
- 能力的使用权、目标 scope、每天次数在规则里不完全统一，需要以规则引擎为准。
- 当前粒子信念未必能识别需要哪个角色，能力链还要和身份推断结合。
