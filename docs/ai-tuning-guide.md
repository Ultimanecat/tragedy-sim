# AI 调优与规则集扩展指南

本文面向以后为新规则集接入或调优 AI 的开发者。目标不是把某个固定剧本的胜率调高，而是建立一条可以重复执行、可以消融、
不会泄露隐藏信息的工程流程。现有策略与已知限制见 [AI 现状](ai-current-state.md)，实验数字见
[AI 基准结果](ai-benchmark-results.md)，长期优先级见 [路线图](future-roadmap.md)。

## 一、先划清三条边界

### 1. 规则引擎是唯一裁判

AI 只能选择引擎提供的合法行动，并在 `Game` 副本上调用同一状态转移进行模拟。不要在 AI 中复制一份“近似结算规则”，也不要
为了搜索方便跳过强制能力、选择顺序或时间点。新增规则先完成规则引擎与确定性测试，再接 AI。

### 2. 主人公只能读取公开 Observation

剧作家知道真实剧本、身份、事件当事人，因此黑方搜索可以读取完整 `Game`。公平主人公 AI 只能消费
`protagonist_team_view()` 或等价 Observation；真实 `scenario`、`roles`、暗牌牌面、内部失败诊断和服务端 trace 都不能进入决策。

已知剧本 Oracle 是故意作弊的诊断工具，必须与公平 AI 分开命名、分开基准：

- 明牌 Oracle：知道剧本，也知道当天黑方牌面；用于验证“规则模拟与主人公行动候选是否足以防守”。
- 暗牌 Oracle：知道剧本，但只看到当天公开目标；用于验证暗牌采样和混合策略压力。
- 公平粒子 AI：只从公开信息维护可能世界；用于评估真实游戏条件下的棋力。

### 3. 信念、行动搜索和诊断分别计量

证据维护不占 `SearchBudget.node_limit` 或 rollout 深度，但消耗墙钟；行动搜索不得因为 witness 更多而自动减少节点。Trace 至少分别记录：

- witness 编译与重采样耗时；
- 身份、事件当事人、暗牌三个维度的候选数；
- 三牌候选数、世界×对手策略模拟次数；
- 搜索耗时、停止原因与实际 horizon；
- 失败原因、最终猜对人数和能力使用次数。

## 二、新规则集的推荐接入顺序

不要一开始就写公平 ISMCTS。按下面顺序可以把“规则错误”“行动候选不足”“信念错误”分开定位。

1. **规则冒烟**：随机对随机跑完整对局，保证所有阶段都能结束、没有非法行动或死循环。
2. **固定策略黑方**：为主要胜利路线写便宜、可解释的黑方策略，稳定触发角色死亡、事件和轮回末失败。
3. **明牌 Oracle 红方**：知道全部秘密和当天牌面，应在简单、理论上可防守的剧本接近全胜。若失败，先查规则、候选覆盖和 horizon。
4. **暗牌 Oracle 红方**：保留剧本真相，只隐藏当天牌面；用于调整暗牌场景覆盖和最坏情形防守。
5. **公开 witness 与可能世界**：先加入确定性硬证据，再加入有反例保护的软证据。
6. **公平粒子红方**：复用 Oracle 的三牌候选器，把同一候选放到同一批世界上交叉评估，避免逐世界选最佳牌造成策略融合。
7. **更强黑方**：黑方联合搜索应面对多个强弱和风格不同的红方，不能只针对当前公平 AI 的固定弱点。
8. **跨日与学习模型**：只有日内规则、信息边界和回归稳定后，才增加轮回 horizon、跨轮回树、强化学习或神经网络 value。

每个阶段都保留上一阶段作为大厅可选策略和基准，不用“新版”覆盖掉诊断基线。

## 三、如何运行 self-play

### 1. 单一剧本快速烟测

```powershell
python -m benchmarks.ai_self_play `
  --scenario official-btx-06-secret-that-was-kept `
  --games 5 --seed 0 `
  --nodes 8 --depth 8 `
  --protagonist-nodes 8 --protagonist-depth 8 `
  --strategy fixed --protagonists particle_ensemble --progress
```

常用开关：

- `--strategy`：黑方 `random/fixed/naive/optimized/strategic/joint`；
- `--protagonists`：红方基线、Oracle、ISMCTS 或 `particle_ensemble`；
- `--protagonist-horizon day|loop`：公平粒子版默认用 `day`，`loop` 仅作实验消融；
- `--time-limit-ms`、`--protagonist-time-limit-ms`：真正的每决策墙钟比较；
- `--disable-joint-witness`：关闭局部跨维 witness 做消融；
- `--mastermind-policy-samples`：每个可能世界测试的黑方路线数；
- `--information-reward-weight`：微量信息价值开关，设为 0 可做干净消融；
- `--json`：输出完整 trace，适合保存失败局审计，但输出可能很大。

节点数相同不等于用时相同。棋力报告至少分两档：

- **秒级档**：快速覆盖全部剧本和多个种子，定位规则或策略异常；
- **分钟档**：只跑已通过正确性审计的代表局面，比较算法随预算增长的收益。

超大预算只能用于估计剧本平衡性或构建参考值，不能替代多种子测试。

### 2. 标准 / Easy 轮回数配对

```powershell
python -m benchmarks.ai_difficulty_matrix `
  --module BTX `
  --scenario-base official-btx-06-secret-that-was-kept `
  --games 5 --seed 0 `
  --nodes 4 --depth 6 `
  --protagonist-nodes 4 --protagonist-depth 6 `
  --mastermind fixed --protagonists particle_ensemble
```

同一秘密、相同种子和预算必须成对比较。额外轮回理论上不会降低最优策略价值；若 Easy 反而更差，优先检查粒子随机漂移、
witness 权重、候选覆盖、最终猜测和回退路径，不要解释成剧本难度真的反转。

### 3. 每次改动的最小实验矩阵

一次 witness、候选或奖励改动至少包含：

1. 一个能触发目标现象的构造测试；
2. 一个“相似但不应触发”的反例；
3. 已知失败 seed 的修改前后定点回放；
4. 关闭该特性的消融组；
5. 至少一个其它剧本和旧规则集回归；
6. 全套 `python -m unittest discover -s tests`。

报告胜率之外还要报告平均失败轮回、各失败原因、最终猜对人数、真实世界是否仍通过全部硬 witness、候选数、实际耗时和置信区间。
低样本结果写成“工程回归”，不能写成稳定棋力结论。

## 四、如何设计 witness

### 1. 从公开现象开始，不从真实原因开始

witness 的输入只能是该座位能看到的结构化事件。正确的问题是：

> 观察到现象 O 后，哪些隐藏世界仍能按照规则产生 O？

而不是：

> 引擎内部说原因是身份 R，怎样把 R 告诉 AI？

每条 witness 应包含 `kind/subject/value/loop/day/timing/source/strength`，让 trace 能回答“哪条公开证据何时改变了这个世界”。
匹配器返回 `SATISFIED / CONTRADICTED / UNKNOWN`；只有硬 witness 的 `CONTRADICTED` 才能删除世界。

### 2. 硬 witness 的判定清单

只有同时满足以下条件才使用 `HARD`：

- 现象对主人公公开；
- 触发是强制的，或结果已经被规则明确公开；
- 时间点状态有日志快照，不是拿今天棋盘倒推过去；
- 已穷尽替代身份、临时身份、替代主规则和同时触发的能力；
- 所有合法解释都排除该候选世界。

典型硬证据包括已公开的身份、规则、事件当事人，以及事件“确实发生”时可见计数物满足公开阈值。可选能力没有发动、玩家没有
采取某个看似最优行动、黑方没有使用某技能，通常都不是硬证据。

### 3. 事件发生／未发生

事件判定时应把必要的公开状态冻结进日志：当事人的不安、好感、密谋、存活／在场、位置、护卫和规则集额外资源。随后：

- **事件发生**：若某候选当事人在该快照下必不可能发动，可用硬 witness 排除；
- **事件未发生**：死亡、拒绝、无效化、身份能力或可选结算都可能解释缺席，默认只做软证据或 `UNKNOWN`；
- **事件当事人公开**：直接生成 `culprit_is`；
- **替换当事人／伪装事件**：必须由规则集 matcher 同时列出原当事人和替代者，不要让通用编译器猜测。

测试至少覆盖：刚好达到阈值、低一格、当事人死亡、被护卫、临时身份、旧 replay 没有快照。

### 4. 人物死亡

死亡本身通常不能直接证明凶手或死者身份。建议拆成多个有限软因子：

- `day_end_death_companion`：日末同区域仍存活的角色集合，支持强制杀人身份；
- 死者的公开计数物和临时身份状态；
- `loss_after_death`：死亡后紧接轮回失败，支持死者是关键人物类身份；
- 事件阶段死亡：与当天事件及当事人快照关联，不能套用日末同伴推理。

同一时间点可能先同时触发多个强制能力，再按玩家选择结算可选能力；例如两名杀人狂单独相处会同时死亡。Witness 必须依据最终公开
结算与时间点规则列出全部解释，不能按某个内部执行顺序错误地判定只有一名凶手。

BTX 等规则集还要考虑普通人被病毒临时变成杀人狂、因子临时获得关键人物能力等。最终猜测问的是初始身份时，公开的当前身份
不能直接写成初始身份硬证据。

### 5. 轮回结束失败

首先区分失败时间点：事件阶段失败、日末失败、最后一天结束失败、轮回耗尽后的最终猜测失败不是同一现象。日志和界面必须保存
精确时间点，witness 只匹配对应阶段。

轮回失败应按公开条件拆解：

1. 重放该轮公开计数物与事件状态；
2. 列出当时所有可能满足的主规则／身份失败路线；
3. 单一维度事实写 `plot_pressure` 或 `role_pressure`；
4. “规则 P 且候选集合中有人是身份 R”写局部 `joint_plot_role_pressure`；
5. 多条路线可能同时成立时全部保留为软证据，不把未被选中的路线降为零。

例：某角色初始区域密谋达到 2 后正常日末失败，可以同时产生“定时炸弹”主规则压力，以及“该区域初始角色中存在魔女”的联合
压力。两者可以帮助下一轮防守该区域，但仍不能硬排除最后日时间旅行者、其它同时失败路线或可选能力差异。

### 6. 能力接受、拒绝和缺席

- 明确因身份而拒绝可拒绝的好感能力，可以生成 `role_in`；
- 同日已经使用、再次声明而无效果，不能误记成身份拒绝；
- 接受能力不等于排除“本可拒绝但选择接受”的身份；
- 可选能力未发动只能进入行为模型，不能写成规则硬 witness；
- 信息类能力重复获得同一事实时，信息价值应为零或显著递减。

### 7. 分维信念与局部关联

默认分别维护：

- 身份／主规则；
- 每日事件当事人；
- 当前剧作家暗牌；
- 剧作家历史放牌倾向（行为后验，不是规则 witness）。

只有独立维度无法表达关键因果时才加小型联合因子，例如“炸弹×魔女初始区域”。不要直接恢复成身份×事件×暗牌的巨大联合粒子；
这会迅速耗尽样本。软 witness 可以为实际合法候选打分并重新采样，避免粒子只删不补。

### 8. 新 witness 的测试模板

每种现象至少测试：

- 编译器从公开事件生成预期字段和时间点；
- matcher 对满足、矛盾、未知世界分别返回正确三值；
- 硬证据删除矛盾世界，软证据只改变分数；
- 真实剧本始终通过所有硬 witness；
- 关闭该 witness 后行动预算不变；
- 重复证据按通道封顶，不因次数无限放大；
- Observation 删除私有字段后结果不变，防止真相泄漏。

规则集专有逻辑应放在专有 compiler/matcher 或注册模块中；通用粒子容器和搜索器不应出现大量规则集名称判断。

## 五、如何设计启发式候选和奖励

### 1. 先区分“候选先验”和“价值奖励”

- **候选先验**决定哪些合法行动更早进入有限候选池，例如黑方在区域放牌时，至少生成一组对该区域使用禁止密谋的三牌。
- **价值奖励**只在已模拟的候选间排序，例如对公开区域威胁给予有界防守奖励。

关键行动若根本不在候选池，提高奖励没有用；反过来，仅加入候选而估值完全看不到跨日风险，也可能永远不选。

候选先验不能永久剪除其它合法行动。预算扩大时应逐步加入低先验组合，并保留朴素未剪枝算法作为对照。

### 2. 奖励的排序层级

推荐使用字典序而不是把所有目标粗暴相加：

1. 整局／当前 horizon 是否存活；
2. 当日是否存活；
3. 最坏粒子或低分位值；
4. 日末局面值；
5. 平均值；
6. 有界启发式与信息微奖励。

若某奖励加入尾部值或日末值，也必须保证所有存活维度先比较。测试应构造“奖励很高但会死”的反例，确认它永远不能战胜安全计划。

### 3. 通用启发式

通用启发式只能使用跨规则集含义稳定的公开事实，例如：

- 当天黑方在区域放牌时，生成一个禁止该区域密谋的候选；
- 已知关键人物不应与已知杀人狂单独相处；
- 临近公开事件时，降低已知当事人的不安；
- 同一玩家同日不能对同一目标重复放置不允许叠加的牌；
- 已经公开无收益或重复的信息能力不再获得信息奖励。

即便如此也必须可关闭并做跨剧本消融。当前地点防守奖励为 0.08，低于任何存活率差异，只说明这是一个工程先验，不是永久常数。

### 4. 规则集限定启发式

规则集专有胜负条件应由 `(scenario setup, current state)` 的条件化估值器或规则集策略模块处理。例如：

- FS“守护此地”关注学校密谋；
- BTX“定时炸弹”关注魔女的轮回初始区域；
- 最后一天时间旅行者友好不足是“最后一天结束时”失败，而非轮回耗尽失败；
- 其它规则集的 EX 卡、魔法、世界线或尸体资源必须在各自时间点估值。

不要硬编码“剧本编号 → 固定行动”。应从主规则、身份槽、事件日程和当前状态动态推导目标，这样同一算法才可用于公平多世界 AI。

### 5. 信息价值

不要用固定奖励强迫 AI 多打友好牌。信息价值至少取决于：

- 该能力能排除多少当前仍有权重的世界；
- 当前好感与未来剩余友好牌能否在本轮实际达到阈值；
- 一轮一次、仅首轮后可用等限制；
- 目标身份是否已经确定；
- 重复调查是否会得到新信息；
- 当前是否必须先防止立即失败。

信息奖励应严格小于存活目标，并单独记录 `future/realized/refusal`。是否值得故意输掉本轮换证据应由跨轮回搜索或学习型整局价值
决定，不能由单日固定常数拍脑袋。

### 6. 何时用学习型估值

只有在以下条件满足后再训练：规则结算稳定；公开状态编码不含私有字段；self-play 数据可复现；训练／验证剧本分离；手写基线和
消融完整。第一版 value 模型只预测整局胜负，并与同墙钟手写估值比较。策略网络、强化学习和剧本平衡性超大预算评估放在之后。

## 六、失败局的诊断顺序

看到异常失败时按以下顺序排查，避免直接调权重：

1. **规则是否正确**：回放时间点、强制／可选顺序、牌抵消和失败原因。
2. **行动是否合法且有效**：是否生成了同日重复牌、对区域使用无效牌、把三人的限次牌误当成全队一张。
3. **Oracle 能否防住**：明牌 Oracle 失败通常是候选或 horizon 问题，而不是信念问题。
4. **关键防守是否进入候选**：若没有，修候选覆盖；不要先提高估值。
5. **真实世界是否被硬 witness 误删**：这是正确性错误，优先级最高。
6. **真实世界是否只是没被有限样本抽到**：扩大或改进求解器，不要把“未抽中”说成证据反驳。
7. **软后验是否合理**：检查每条 witness 的贡献、通道封顶和跨维关联。
8. **暗牌／对手路线是否覆盖**：不能从少量随机样本全活推断必活。
9. **horizon 是否足够**：日末值看不到轮回末炸弹、限次牌保存和未来事件时，再比较 loop/match，而非盲目加深。
10. **是否过拟合单一 seed**：修复后必须跑相邻 seed、其它剧本、关闭特性的消融和旧规则集回归。

同一个原因重复失败是最有价值的报警：它可能表示证据没生成、证据没进入采样、候选没响应证据，或价值函数看不到未来后果。Trace
应让这四段链路分别可观察。
